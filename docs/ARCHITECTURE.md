# Architecture Document
## TRELLIS Forge v1.0 - Component View

**Product**: TRELLIS Forge
**Version**: 1.0.0 (Initial Windows Release)
**Date**: 2026-01-20
**Status**: Production-Ready (Internal/Demo)

---

## 1. Executive Summary

TRELLIS Forge is architected as a single-process Python application with a layered design separating presentation (Gradio UI), application logic (pipeline orchestration), and infrastructure (CUDA rendering). The system is optimized for single-user GPU-accelerated 3D generation on Windows platforms.

**Architectural Principles**:
- **Simplicity**: Monolithic design for ease of deployment
- **GPU-First**: All compute-intensive operations run on CUDA
- **Stateless Sessions**: No persistent storage, temp files only
- **Fallback-Ready**: Graceful degradation on CUDA errors


## 8. Design Patterns

### 8.1 Architectural Patterns

**Monolithic Architecture**:
- Single Python process
- All components in one codebase
- Shared memory space
- No microservices or distributed components

**Layered Architecture**:
- Presentation: Gradio UI components
- Application: Orchestration functions
- Domain: TRELLIS pipeline, rendering utilities
- Infrastructure: CUDA backends, representations

### 8.2 Design Patterns Used

**Facade Pattern**:
- `TrellisImageTo3DPipeline` provides simple interface to complex model
- Hides details of VAE, flow transformers, decoders

**Adapter Pattern**:
- `gsplat_wrapper.py` adapts gsplat API to diff_gaussian API
- Ensures drop-in compatibility

**Strategy Pattern**:
- Rendering backend selection:
  - Strategy 1: diff_gaussian_rasterization
  - Strategy 2: gsplat_wrapper
  - Strategy 3: Fallback to black image

**State Pattern** (Implicit):
- Gradio component states:
  - Button enabled/disabled based on generation completion
  - Download buttons enabled/disabled based on extraction

**Template Method Pattern**:
- `pipeline.run()` defines generation steps
- Subclasses can override sampling strategies

### 8.3 Anti-Patterns Avoided

**God Object**: Avoided by layering
- `app.py` is thin orchestrator (not God object)
- Domain logic in pipeline, not in UI layer

**Premature Optimization**: Avoided
- No custom CUDA kernels (use gsplat)
- No manual memory pooling (trust PyTorch)
- No multithreading complexity (single-user sufficient)

**Tight Coupling**: Minimized
- Rendering backends swappable (gsplat vs diff_gaussian)
- Pipeline independent of UI (can be used standalone)

## 9. Quality Attributes

### 9.1 Performance

**Latency**:
- Generation: ~4 seconds (target: <10 seconds) ✅
- GLB export: ~30 seconds (target: <60 seconds) ✅
- Gaussian export: ~2 seconds (target: <5 seconds) ✅

**Throughput**:
- Current: ~15 generations/hour (single user)
- Scalability: N GPUs = N concurrent users

### 9.2 Scalability

**Vertical Scaling** (Single Machine):
- Add more GPUs → Linear scaling
- Bottleneck: PCIe bandwidth (multi-GPU data transfer)

**Horizontal Scaling** (Multi-Machine):
- Requires queue system (Redis/RabbitMQ)
- Stateless workers enable horizontal scaling
- Bottleneck: Network latency for file transfers

### 9.3 Reliability

**Availability**:
- Current: No HA (single process)
- SPOF: Python process crash = full downtime

**Fault Tolerance**:
- Fallback rendering (gsplat → black image)
- Session isolation (user crash doesn't affect others)

**Recovery**:
- No automatic restart
- Manual intervention required on crash

### 9.4 Maintainability

**Modularity**:
- Clear separation of concerns (presentation, application, domain, infrastructure)
- Components loosely coupled

**Testability**:
- Functions are pure (input → output, no hidden state)
- Integration tests verify end-to-end
- Unit tests possible but not implemented

**Documentation**:
- Code comments minimal
- Function docstrings present
- External documentation comprehensive (this document)

### 9.5 Security

**Confidentiality**: Low (no sensitive data)
**Integrity**: Medium (input validation minimal)
**Availability**: Low (no DoS protection)
**Authentication**: None
**Authorization**: None

## 10. Technology Decisions

### 10.1 Technology Selection Rationale

| Technology | Alternatives Considered | Decision Rationale |
|------------|-------------------------|-------------------|
| **Gradio** | Streamlit, Flask+React | Rapid prototyping, built-in 3D viewer, session management |
| **PyTorch** | TensorFlow, JAX | Ecosystem (transformers, diffusers), CUDA support, pretrained models |
| **gsplat** | diff_gaussian_rasterization | Windows compatibility (diff_gaussian build fails), active development |
| **trimesh** | Open3D, PyMesh | Simplicity, robust simplification, GLB export |
| **rembg** | Manual masking, GrabCut | Automatic, high quality, U2Net pretrained |
| **xformers** | flash-attn, vanilla attention | Windows compatible (flash-attn fails), efficient |

### 10.2 Trade-Offs

**gsplat vs diff_gaussian_rasterization**:
- **Pro**: Windows CUDA compilation works
- **Con**: API differences require wrapper, slightly slower
- **Decision**: Use gsplat with compatibility wrapper

**Single Process vs Microservices**:
- **Pro**: Simple deployment, no network overhead
- **Con**: No horizontal scaling, SPOF
- **Decision**: Monolith for v1.0, microservices for v2.0 if needed

**In-Memory State vs Database**:
- **Pro**: Fast, no I/O overhead
- **Con**: Lost on disconnect, no persistence
- **Decision**: In-memory for demo, database for production
